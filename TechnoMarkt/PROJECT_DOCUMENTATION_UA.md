# Технічна документація проекту "TechnoMarkt"
## Тема курсової: Мережа магазинів побутової та будівельної техніки

Цей документ призначений для глибокого ознайомлення з архітектурою, логікою та технічною реалізацією проекту "TechnoMarkt".

---

### 1. Архітектурна парадигма: Vertical Slicing & SOLID
Проект побудований на принципах **Feature-First** (спочатку функціональність). На відміну від класичного MVC, де всі моделі лежать в одній папці, а контролери в іншій, тут проект розділений на "вертикальні зрізи" (Areas).

**Переваги такої структури:**
*   **Висока когезія (High Cohesion):** Весь код, що стосується однієї фічі (наприклад, управління складом), локалізований в одному місці.
*   **Розділення інтерфейсів (ISP):** Контролери не працюють з гігантськими монолітними сервісами. Вони отримують лише ті інтерфейси, які їм потрібні (наприклад, лише для читання або лише для статистики).

---

### 2. Детальний опис рівнів системи

#### 2.1. Рівень даних (Data & Models)
Використовується **Entity Framework Core 8** з підходом **Code First**.
*   **AppDbContext:** Центральний вузол доступу до БД, налаштований на використання SQL Server.
*   **Fluent API:** Використовується для налаштування складних зв'язків (наприклад, каскадне видалення або точність десяткових чисел для фінансів).
*   **Ключові сутності:**
    *   Item: ID, Назва, Ціна, КатегоріяID, Опис.
    *   Warehouse: МагазинID, ТоварID, Кількість, Дата останньої поставки.
    *   Order: КлієнтID, МагазинID, Дата, Статус (New, Processing, Ready, Completed, Cancelled).
    *   Transaction: Сума, Тип (Income/Outcome), Метод оплати, Дата.

#### 2.2. Рівень бізнес-логіки (SOLID Services)
Кожна доменна область розділена на спеціалізовані сервіси:

**Приклад: Модуль "Склад" (Stock)**
*   IStockReadService: Методи GetStockItemsAsync з підтримкою складної фільтрації (за назвою, категорією, критичним залишком).
*   IStockEditService: Методи RestockItemAsync (поповнення) та AdjustInventoryAsync (інвентаризація).
*   IStockStatsService: Розрахунок KPI: загальна вартість товарів на складі, кількість позицій "поза стоком", критичні залишки.

#### 2.3. Рівень представлення (MVC & UI)
*   **Areas:**
    *   Administrator: Фінансовий моніторинг, управління персоналом, системні налаштування.
    *   Manager: Управління каталогом, знижками та постачальниками.
    *   Operator: Операційне управління замовленнями в магазині.
    *   Client: Особистий кабінет клієнта, покупки, гаманець.
*   **ViewComponents:** Використовуються для ізольованої логіки (наприклад, OrderDetailsViewComponent для відображення складу замовлення в модальному вікні).

### 3. Функціональні можливості за ролями (Детально)

#### 3.1. Адміністрування та Фінанси
*   **Дашборд:** Візуалізація продажів за допомогою графіків (Daily Sales, Revenue by Quarter).
*   **Звітність:** Генерація фінансових звітів у форматі PDF за допомогою ReportService (використовує рендеринг Razor-вьюх у PDF-потік).
*   **Логування:** Система EventLogs фіксує всі критичні дії (зміна цін, видалення товарів, зміна статусів замовлень) для аудиту.

#### 3.2. Операційна діяльність (Склад та Замовлення)
*   **Склад:** Система автоматично підсвічує товари, кількість яких нижче критичного порогу.
*   **Замовлення:** Повний життєвий цикл замовлення від "Нового" до "Виданого" або "Повернутого". При поверненні товару протягом 14 днів система автоматично перераховує залишки на складі та повертає кошти на гаманець клієнта.

---

### 4. Реалізація безпеки та валідації
*   **Автентифікація:** Використовується **ASP.NET Core Identity**. Користувачі розділені за ролями (Role-based Authorization).
*   **Валідація:** 
    *   На рівні моделей: [Required], [StringLength], [Range] для базових перевірок.
    *   На рівні сервісів: Перевірка бізнес-правил (наприклад, неможливість замовити товару більше, ніж є на складі).
*   **Анти-фрод:** Використання [ValidateAntiForgeryToken] у всіх POST-запитах для захисту від CSRF-атак.

---

### 5. Структура файлової системи (Convention)
Для зручності навігації в кожній Area дотримується структура:
`	ext
/Areas/[FeatureName]/
├── Controllers/       # Контролери з мінімальною логікою
├── ViewModels/        # Моделі лише для відображення
│   ├── Forms/         # Моделі для форм (Input)
│   ├── Tables/        # Моделі для таблиць (Output)
│   └── Kpi/           # Моделі для статистичних показників
├── Views/             # Razor-шаблони
└── Services/          # (Опційно) Специфічні для Area сервіси
`

### 6. Висновки щодо якості коду
Після рефакторингу проект демонструє:
1.  **Low Coupling (Низька зв'язність):** Зміни в одному модулі (наприклад, Знижки) не впливають на інші модулі (наприклад, Фінанси).
2.  **High Reusability:** Завдяки винесенню спільних моделей та інтерфейсів у Shared, код легко перевикористовується.
3.  **Clean Code:** Відсутність "магічних чисел", використання констант, чітке іменування методів та асинхронне програмування (sync/await) по всьому проекту.
